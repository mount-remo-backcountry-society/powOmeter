# Independent review: POW-O-METER data platform v2 (design draft v3)

**Reviewer:** Claude (Fable 5.1), 2026-10-02. Read-only review per `docs/REVIEW_BRIEF.md`.
Judged only from the files the brief lists plus public web documentation.
Not read: `misc/`, `data/Google Sheet/`, `data/Aquarius/`, the `Approx Lat/Lng`
column of the RockBLOCK export, the firmware beyond one grep.

Labels: **Confirmed** = I checked it (file:line, command, or document).
**Plausible** = reasoned from the design, not tested.

---

## 1. Verdict

**Sound with changes.** The architecture (raw immutable, corrections as data,
rebuild from raw, static publication, one-way dependency) is the right shape
for R1–R6, and the September failures justify it. Four things should change
before code is written, because the design as drafted would build them in:
publish only after the MRBS organisation exists (Pages URLs do not survive a
transfer); separate publishing from alerting (a failed build cannot publish
its own alarm, and alert emails go to whoever last edited the cron line);
freeze approved periods as snapshots (they cannot be both "never changed" and
"rebuilt from raw every run"); and define snow depth as a derivation with a
per-firmware-era statistic, not as a correction. The rest is detail that can
be settled while building, as the owner intends.

---

## 2. Findings, most important first

### F1. Create the MRBS organisation before Phase 2, not "until then" (§4, §13) — Confirmed

- **Issue.** Phase 2 publishes `v1/` files whose URL becomes the external
  interface for Avalanche Canada and powWX. The design starts under
  `j-krick` and transfers later. GitHub redirects repository links after a
  transfer, but **"we don't redirect GitHub Pages associated with the
  repository."** The published URL changes at transfer, so every consumer
  breaks at exactly the moment the project is handed over.
- **Evidence.** GitHub docs, "Transferring a repository":
  https://docs.github.com/en/repositories/creating-and-managing-repositories/transferring-a-repository
- **Impact.** R3 (handover breaks consumers), R4 (powWX would need a
  coordinated change), R5 (a second station would inherit the wrong URL).
- **Change.** Make the MRBS organisation (free) and the second owner Phase 0
  exit criteria. If that is politically slow, build in Julian's account but
  do not give the URL to anyone until the transfer is done. A custom domain
  would also decouple the URL but costs money (R1) and adds DNS to the
  handover.

### F2. Alerting by failing the build is partly silent and routes to the wrong person (§5.7, §6.7) — Confirmed

- **Issue 1: a failed build publishes nothing.** §6.7 says the build fails
  on a health problem and "the same state appears in `status.json` and on
  the site". If the build fails, Pages is not deployed, so the site keeps
  showing the previous `status.json`. The site cannot show "station silent"
  unless the age is computed in the browser from the viewer's clock, which
  the design does not say.
- **Issue 2: one bad payload stops all publishing.** "A payload fails to
  decode" is a build failure, so one malformed message (they exist: MOMSN
  2941 was a `No Data` session; `IMPROVEMENTS.md` Part 1 item 9 describes
  unparseable fields from old firmware) halts every output until someone
  edits code.
- **Issue 3: who gets the email.** "Notifications for scheduled workflows
  are sent to the user who initially created the workflow"; if someone
  edits the cron line, to that user; if the workflow is re-enabled after the
  60-day pause, to whoever re-enabled it. After Julian leaves, the emails go
  to Julian.
  https://docs.github.com/en/actions/monitoring-and-troubleshooting-workflows/monitoring-workflows/notifications-for-workflow-runs
- **Issue 4: alert fatigue.** A station that dies in season fails the hourly
  build 24 times a day until a human edits `monitoring.yaml`. A
  non-programmer successor gets 24 emails a day and no way to say "known".
- **Impact.** R6 (stale data looks current), R3 (alerts reach the wrong
  person; a successor cannot silence them).
- **Change.** Split into two jobs: *publish* always runs and writes the
  alarm state into `status.json`; *check* runs after publish and fails only
  on state change (new alarm, or alarm cleared). Compute data age in the
  browser from the viewer's clock and the last observation time. Decode
  errors set `quality: missing` plus a qualifier and count in `status.json`
  rather than failing. Route alerts through something a non-programmer can
  own: the check job opens or comments on a GitHub Issue and the MRBS
  owners watch the repo, so recipients are managed in GitHub settings, not
  in a workflow file.

### F3. The 60-day rule is real; the mitigation can still die silently (§14) — Confirmed rule, Plausible mitigation

- **Issue.** "In a public repository, scheduled workflows are automatically
  disabled when no repository activity has occurred in 60 days." The docs do
  not define "activity" and do not say whether commits made by the build's
  own token count. If the schedule is disabled there is no build, hence no
  failure, hence no email: a completely silent death, most likely in the
  quiet summer. A "season-aware schedule" makes this more likely, not less.
  https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows
- **Also:** the schedule "can be delayed during periods of high loads …
  High load times include the start of every hour." Do not schedule on the
  hour, and do not promise hourly latency.
- **R1 note (Confirmed).** Actions is free only for *public* repositories on
  standard runners. On the Free plan a private repository gets 2,000
  minutes a month; an hourly build at about 3 minutes uses about 2,200. If a
  future owner makes the repository private "for privacy", it starts
  failing or costing money.
  https://docs.github.com/en/billing/managing-billing-for-your-products/managing-billing-for-github-actions/about-billing-for-github-actions
- **Change.** Keep one commit a month from a human or a dated keepalive
  file, put "open the site and check the build date" in `OPERATIONS.md` as
  a first-of-month task, and record the public-only cost rule in
  `README.md`. Consider a free external dead-man's switch only if it needs
  no secret.

### F4. "Approved" periods and "full rebuild from raw" contradict each other (§6.4, §8.3) — Plausible

- **Issue.** §8.3: "Automatic processing never changes an Approved period."
  §6.4: "Full rebuild from raw on every run … so every correction applies
  retroactively." A fix to the payload decoder, the timing rule, or a QC
  threshold changes the output for an Approved period on the next run. The
  rule as written is unenforceable. Also undefined: what happens when a new
  SD download or a new raw message lands inside an Approved period.
- **Impact.** R6 and data integrity: an approved season can change
  silently, which is the failure Aquarius approval exists to prevent.
- **Change.** Approving a period commits a snapshot file (for example
  `approved/powometer/2025-26/snow_depth.csv` with a hash). The build
  publishes the snapshot for approved periods and *also* regenerates them;
  a difference becomes a warning in `status.json`, never a silent change.
  This is one extra file per approval and keeps the operation log honest.

### F5. Radio distance changed statistic on 2026-09-26; the merge rule does not know (§6.4, §6.6) — Confirmed

- **Issue.** Before v1.3 the radio sent the *minimum* of the burst; v1.3
  sends the *median* (`IMPROVEMENTS.md` Part 1 item 8: the minimum sits
  about 69 mm below the median). SD has min, max and median
  (`scripts/clean_sd_data.py:308-319`). The design has one variable
  `distance_to_surface` and a `statistic` column but no rule mapping radio
  readings to `min` before 2026-09-26 and `median` after. "SD authoritative,
  radio fills the rest" would then mix statistics in one series, with a
  7 cm step in snow depth wherever radio fills a gap in old data.
- **Impact.** R6 (a 7 cm artefact in snow depth), data integrity.
- **Change.** Add `firmware_versions.yaml` (version, deployed-from, radio
  statistic, no-echo sentinel values 498/499/500). The decoder stamps
  `statistic` from it. Publish `snow_depth` with an explicit statistic and
  state which one `best.csv` uses (median, per CIMO).

### F6. Snow depth is a derivation, not a correction (§6.3, §8.2 example C002) — Confirmed context, Plausible fix

- **Issue.** C002 applies the zero-depth reference as an `offset` operation
  at level `corrected`. Then `raw` and `qc` levels either have no
  `snow_depth` or one computed from an undefined reference. The project has
  already been burned by reference ambiguity: "sensor height" in the Field
  tab looks about 0.5 m too small, depth sits on a −0.54 to −0.7 m floor and
  about 25 % of values are negative (`IMPROVEMENTS.md` Part 4 item 3;
  `data/Cleaned/README.md:103-108`). `field_visits.yaml` lists both "sensor
  height above ground" and "zero-depth distance" without saying which one
  the derivation uses.
- **Change.** Define once: `snow_depth = zero_depth_distance − distance`,
  where zero-depth distance is sensor face to bare ground, measured at
  install and each season end, recorded in `field_visits.yaml` with a
  from-date. Apply it at every level. Corrections handle drift and offsets
  *beyond* that reference. QC flags negative depth as `suspect` rather than
  clipping.

### F7. Hour-ending means do not match what consumers compare against (§6.4, §6.6, §9) — Confirmed context, Plausible impact

- **Issue.** The design stamps hourly values at the end of the hour,
  implying a mean over the preceding hour. Today's consumers use
  instantaneous values at :00: the Apps Script interpolates to the hour
  (`scripts/Google Apps script v2.js:474-528`), powWX interpolates to the
  hour to align with forecasts (`powwx/observations.py:156-198`), and the
  Avalanche Canada feed for station #58 reports at :00 UTC with a `Z`
  suffix (checked 2026-10-02:
  `https://weather.prod.avalanche.ca/stations/58/measurements`). A
  preceding-hour mean is centred on :30, so comparisons with forecasts or
  neighbours valid at :00 carry a 30-minute phase lag.
- **Impact.** R4 (powWX verification quality), R6 (overlay of nearby
  stations misaligned by half an hour), and the CF/WaterML citation is
  correct but answers a different question than "what do consumers need".
- **Change.** Publish the ~17-minute `point` readings (they are the data)
  and an on-the-hour instantaneous series with `statistic: point` and
  qualifier `interpolated`, which matches current practice. If a mean is
  wanted, publish it as a separate `statistic: mean` with `time_start_utc`.
  Record each third-party source's time convention in `sites.json`.

### F8. The sheet-to-repo copy is unspecified, and the choice decides whether the repo needs a secret (§6.1) — Plausible

- **Issue.** The job that copies `Messages` rows into `raw/radio/` needs
  either a Google service-account key in Actions secrets (a secret to
  rotate at handover, and a second service account next to Avalanche
  Canada's) or a "publish to web" CSV link (no secret, public, cached a few
  minutes). The design does not say. Reading cells through the API also
  hits the timezone trap the script itself documents
  (`scripts/Google Apps script v2.js:372-378`): Sheets converts the
  `Transmit Time (UTC)` strings to dates in the spreadsheet's timezone.
- **Change.** Publish the `Messages` tab as CSV and pull it with plain
  HTTP in the Action. No secret anywhere in the station repo. Parse the
  text, never a date cell.

### F9. Historic sheet rows still carry the DST hour, and both consumers read them (§3, §12) — Plausible

- **Issue.** Rows written before 2026-09-22 were formatted in
  `America/Los_Angeles` (`IMPROVEMENTS.md` Part 3 item 2); the de-dupe kept
  6,667 of them without re-timestamping. powWX reads the whole tab as fixed
  UTC−8 (`powwx/observations.py:34`), so its historical POW-O-METER series
  is one hour off from March to November, and Avalanche Canada reads the
  same tab. I could not open the sheet to confirm the rows were not
  regenerated.
- **Change.** Once Phase 1 reproduces the record, regenerate the `Data` tab
  from `v1/` outside the season, or publish an erratum in the tab and tell
  both consumers. Add "sheet rows before 2026-09-22 are America/Los_Angeles"
  to `SCHEMA.md` if they stay.

### F10. Privacy plan: one safeguard would leak the thing it protects (§10) — Confirmed

- **Issue.** "A pre-commit hook and a CI check reject … coordinates near
  home." A CI check lives in the repository, so it would carry the home
  coordinates or a box around them. The hook cannot be public.
- **Also found (Confirmed):**
  - `scripts/Google Apps script v2.js:43-45` and `:587-588` hold the IMEI
    and spreadsheet ID; the design plans to move them to Properties, so the
    committed copy must be scrubbed, including the test samples.
  - `scripts/Google Apps script.txt:3` holds a personal email address
    (design already keeps it local).
  - `claude resume session 2026-09-30.txt` in the project root is harmless
    (a session id) but is not in the local-only list.
  - The SD files (`DATA`, `LOG`, `TRACKING`, `TRANSMIT`) contain no
    coordinates, IMEI or addresses (grep over all `LOG.CSV`).
  - There is no `.git` directory yet, so Phase 0 can be done before any
    history exists.
  - Volunteer names in `field_visits.yaml` ("who") are personal data in a
    public repo; use initials or ask.
- **Change.** CI checks only patterns (15-digit IMEI, the spreadsheet ID
  pattern, email addresses). The home-coordinate check stays local, as a
  hook installed by hand, and the sanitised RockBLOCK export simply drops
  the `Approx Lat/Lng` column for every row rather than classifying rows.

### F11. Licensing (§10) is right; three gaps — Confirmed

- **Confirmed.** The BC Data Catalogue record for "Avalanche and Weather
  Programs - Public Access Weather System (PAWS)" carries licence id 22,
  title "Access Only"; the linked page says "the materials are 'access
  only' and reproduction is not permitted without written permission."
  The "Weather Station Network" (locations) record carries the Open
  Government Licence - British Columbia.
  https://catalogue.data.gov.bc.ca/api/3/action/package_show?id=5fc4f181-a796-4449-a152-2fa95523ed32
  https://www2.gov.bc.ca/gov/content?id=1AAACC9C65754E4D89A118B875E0FBDA
- **Gap 1.** The PAWS record's publish state is **"PENDING ARCHIVE"** (July
  2025). Save a copy of the record now, because the citation may vanish.
- **Gap 2.** powWX *already* redistributes MoTI #58 values: hourly values
  are committed to a public repository
  (`.github/workflows/obs-logger.yml:41`, `data/observations/`), PCDS
  history is imported (`README.md:100-113`), and the viewer publishes them.
  The design notes it (§9) but assigns no action. The permission request
  should name both projects and both uses, display and download, and the
  PCDS-sourced history. Until then this is Julian's personal exposure, but
  it is the same data and the same ministry.
- **Gap 3.** Display-only is not a safe fallback. Rendering values on a
  public web page is reproduction in the ordinary copyright sense; the
  design already marks this unverified. Treat "no permission" as "no MoTI
  values on the site" for both projects, which §10 does for the station
  site only.
- Avalanche Canada publishes no terms for its station API that I could
  find; the research report says the same.

### F13. Outputs are over-specified; the processing is under-specified (§6.6, §13) — Plausible

- **Over.** Ten published files per station (`raw.csv`, `qc.csv`,
  `corrected.csv`, `best.csv`, `best_recent.json`, `observations.parquet`,
  `datapackage.json`, `sites.json`, `status.json`, `SCHEMA.md`). Parquet adds
  pyarrow to the build and no reader for a successor; the whole SD record is
  41,554 rows for 17 months (`data/Cleaned/README.md:6`), trivial as CSV.
  `raw.csv` duplicates `raw/`. Suggest: `observations.csv` (all levels, long),
  `best.csv`, `latest.json`, `status.json`, `sites.json`, `datapackage.json`.
  Add Parquet when someone asks.
- **Under.** No tests named for: both DST changes in PCDS conversion;
  overlapping SD downloads (the two 2026-09-26 downloads are near-identical
  copies: 1,535 vs 1,536 "Transmission failed" lines); the
  `(transmit_utc, payload)` key across the console export's
  `29/Sep/2026 18:16:25` format and the sheet's ISO format (22 messages
  overlap since 2026-09-22, a ready-made fixture); the radio statistic
  change (F5). No committed fixture set (sample emails, a small SD folder).
- **Simpler alternative?** No. "Keep the sheet and export CSVs nightly"
  fails R3 and R6 for the reasons in §3. The simplification worth taking is
  fewer outputs and no Parquet in Phase 1, not a different architecture.

### F14. Labels and standards (§6.5, §6.6, §8.2) — mostly Confirmed

- CF names confirmed in standard-name table v95: `surface_snow_thickness`
  (m), `surface_air_pressure` (Pa), `air_temperature` (K),
  `relative_humidity` (1); no entry for distance-to-surface or battery
  voltage. Publishing cm, hPa, °C, % in the `unit` column is fine when
  `datapackage.json` states it.
- WMO registers the quality-flag system as **"WaterML2"** (not
  `WaterML2_0`) at https://codes.wmo.int/wmdr/QualityFlagSystem. Cite it as
  such.
- `approval` values `Working / In Review / Approved` are mixed-case with a
  space, unlike every other label. Use `working / in_review / approved`
  and show "Provisional" on the site for anything not approved, which is
  the USGS public label the research report cites.
- The `delete` operation needs a defined outcome at level `corrected`:
  recommend keep the value, set `quality: poor`, add the qualifier, and have
  `best.csv` drop `poor`. Removing rows makes the record unauditable in the
  published file.
- Hourly snow depth should be `median`, not `mean` (CIMO, research §D).
- The reconstructed 2025-01-31 to 02-17 period (timestamps estimated from
  transmit times, median error 0.7 min) deserves its own qualifier
  (`timestamp_estimated`) distinct from the deterministic
  `timestamp_repaired`.

### F15. Roadmap and the fixed/parked split (§13) — Plausible

- Order is right except that the organisation (F1) and the alert split
  (F2) belong in Phases 0 and 2 respectively, and F5/F6 must be decided
  before Phase 1 code.
- Add to "fixed now": the hourly time convention (F7), station and site id
  strings, and the firmware-era table (F5). These are all in the published
  contract.
- Parked items the core could make hard later: none, with one caveat. The
  review app's "commits through the user's GitHub login. No server" is
  unverified: GitHub's OAuth web flow needs a token exchange that a static
  page cannot do without a proxy. The data model is fine; the "no server"
  claim may not be.
- The RockBLOCK HTTP intake (parked) must answer HTTP 200 within 3 seconds;
  retries use exponential backoff from 1 minute, 14 attempts over about 6
  days (Confirmed: https://docs.groundcontrol.com/iot/rockblock/web-services/receiving-mo-message).
  Email delivery has no documented retry, so the console export remains the
  backstop; `OPERATIONS.md` should include "re-export from the console and
  drop the file into `raw/radio/`", and the loader must accept that format.

### F16. Missing entirely — Plausible

- **A backup of the repository.** Once the laptop is gone, GitHub is the
  only copy of `raw/`. A yearly Zenodo snapshot (already in the research
  report) or a clone on an MRBS drive, written into `OPERATIONS.md`.
- **A raw-immutability check.** A CI rule that fails any change to an
  existing file under `raw/`; today "do not edit" is a README sentence.
- **Local time on the site.** Files in UTC is right; users plan trips in
  Pacific time. Say the site shows `America/Vancouver` and labels it.
- **Schema versioning.** A `schema_version` in `status.json` and a
  `CHANGELOG.md` for the contract, so Avalanche Canada and powWX have one
  place to watch.
- **Decoder per source for R5.** `stations.yaml` has a `type`, but the
  package is described around one payload. Keep decoders keyed by `source`
  so a second station of a different kind is a new module, not a rewrite.
- **Terms of use text** for safety-related data is listed as an open
  question; it should be a Phase 3 exit criterion, since the site is the
  thing users will trust.
- **Fixtures and a `tests/` directory** in the phase list.

## 4. What I did not check

- The live Google Sheet, Apps Script project, trigger ownership, Looker,
  or the Gmail account (no access, and the brief forbids private files).
- Whether commits made by `GITHUB_TOKEN` count as "repository activity"
  for the 60-day rule. GitHub does not document it.
- Whether Ground Control retries email delivery or how long the console
  keeps history. Not documented on the pages I found.
- The firmware beyond the transmission-hour table; `IMPROVEMENTS.md` was
  taken as read.
- Running `clean_sd_data.py`, or the SD data values themselves.
- The research report's Windy, CWOP, Weather Underground, CRMP and CSA
  claims, and the CIMO Guide citations.
- Avalanche Canada's internal use of the sheet, and whether they would
  accept `v1/` files.
- Whether the MB7374 median change (v1.3) actually works on the hardware;
  the first SD download will show.
